# Xinyue AI 当前项目审计与后续执行基线（历史参考）

审计日期：2026-08-18
文档状态：2026-08-18 历史审计；当前状态以 `FINAL_CODE_AUDIT_2026-08-27.md` 和 `LOCAL_CLEANUP_AND_RESTART_2026-08-28.md` 为准
审计原则：以当前代码、数据库迁移和可执行测试为准，不沿用旧文档中的完成标记。

## 1. 结论

Xinyue AI 已经形成一套完整的 Vue/NestJS 商业平台基础，不应再增加第二套登录、用户、管理端、任务队列、模型路由、计费或文件系统。

当前最需要继续处理的不是增加菜单，而是以下五项：

1. 图片工具已具备“专用开源 Worker + 通用图片编辑提示词回退”双路径，仍需用真实 Worker 与模型服务验收。
2. 当前画布具备数据和基础交互，但与 Infinite Canvas 的产品形态和操作深度仍有明显差距。
3. `/api` 已改为后台配置的外部 API 服务入口，不再伪装为本地公共网关。
4. 用户端、管理端和服务端存在几个过大的核心文件，继续叠加功能会增加回归风险。
5. 本地测试覆盖了主要页面和部分真实 API，但支付、模型、搜索、OAuth、邮件、对象存储和图片 Worker 尚未在真实外部环境完成验收。

## 2. 当前架构

```text
用户端：Vue 3 + TypeScript + Vite + Pinia + Vue Router
管理端：Art Design Pro + Vue 3 + Element Plus
服务端：NestJS + Fastify + Prisma
数据库：PostgreSQL
队列与缓存：Redis + BullMQ
Agent：LangGraph.js
画布：Vue Flow
文件：本地磁盘或 S3 兼容对象存储
部署：Docker Compose，图片算法使用可选独立 Worker
```

唯一运行入口：

```text
/          用户端
/admin/    唯一管理端
/v1/       NestJS API
```

## 5. 图片工具最终方向

### 5.1 产品行为

`AI 抠图`、`擦除`、`标记改图`、`扩图`、`变清晰`等卡片始终展示，不因后台没有专用 Worker 而消失。

用户点击卡片后：

1. 切换到对应图片编辑模式。
2. 把后台维护的预设提示词真实写入上方输入框，不只是修改 placeholder。
3. 显示所需输入，例如原图、蒙版或扩展边界。
4. 用户可以继续修改提示词。
5. 用户点击发送后才创建任务，不在点击卡片时自动执行。

### 5.2 执行路径

```text
专用 Worker 已配置且健康
  -> 使用 rembg / IOPaint / Real-ESRGAN / ComfyUI 专用路由

专用 Worker 未配置或未发布
  -> 使用工具预设提示词 + 用户输入 + 原图/蒙版
  -> 交给当前可用的通用图片编辑模型

专用 Worker 和通用图片编辑模型都不可用
  -> 保留输入内容并在提交时明确提示暂无可用模型
```

### 5.3 当前实现

- 前台和画布均使用相同的系统默认目录；后台无记录时卡片仍可见。
- 点击工具会将完整预设提示词写入可编辑输入框，不会自动创建任务。
- 后台按 `toolKey` 覆盖默认工具，并可选择“通用图像模型回退”或“专用本地 Worker”。
- 通用回退不发送虚拟 `creationToolId`，专用 Worker 才会由服务端校验绑定的本地 Worker 模型；没有通用模型时仅在提交阶段报错并保留输入。
- 禁用的后台工具记录会抑制同名系统卡片；创建任务端仍只接受启用的专用工具。

| --- | --- | --- |
| 抠图 | `workers/image-tools` / rembg | 有实现，未做本次真实推理验收 |
| 擦除、局部修复、扩图 | `workers/iopaint` | 有实现，未做本次真实推理验收 |
| 2x/4x 清晰化 | `workers/realesrgan` | 有实现，未做本次真实推理验收 |

## 6. 无限画布真实状态

### 6.1 已实现

- `CanvasDocument` 数据模型和 93 号迁移前后的完整迁移链。
- 创建、读取、更新、复制、归档、删除和修订冲突。
- 自动保存、JSON 导入导出、平移缩放、小地图、节点连线和基础撤销重做。
- 文本、图片、视频、分组和短剧工作流节点。
- 上传素材、关联文件库、生成任务、取消/重试和结果回填。
- 浏览器裁剪与蒙版编辑。
- Canvas Agent 的操作预览和用户确认。
- 套餐中的画布开关、画布数量和节点数量限制。

### 6.2 与 Infinite Canvas 的主要差距

- 当前编辑器仍是 Xinyue 原有 Vue Flow 风格，不是 Infinite Canvas 的工具面板、节点视觉和操作节奏。
- 缺少完整的节点上下文工具栏、移动/交互模式、批量派生生成和丰富节点生态。
- 缺少与参考项目一致的资产拖入、节点级快捷生成、结果分叉、批量排列和多媒体工作流体验。
- Canvas Agent 目前是 Xinyue 的确认式 JSON 操作流，不等同于参考项目的完整画布 Agent 交互。
- OpenTu 的自由白板、流程图、思维导图、Frame、演示预览和 PPT Frame 导出尚未接入画布。
- 管理端目前只有套餐画布权限，没有独立的画布运营、节点能力、默认值、任务统计和问题审计页面。

### 6.3 建议方向

保留现有 `CanvasDocument`、权限、资产、生成、计费和 Agent 后端；重做编辑器交互层和节点组件，不再继续给当前页面零散加按钮。这样可以避免第二套账号和计费，同时允许真正对照 Infinite Canvas 建立功能矩阵。

如果要求源码级快速接近 Infinite Canvas，则需要重新评估直接 fork React 前端的成本；这会引入第二套前端技术栈，不能在没有明确决定时混入当前 Vue 编辑器。

## 7. 短剧与 VOZEB 状态

当前画布已有 `SHORT_DRAMA` 类型、剧本拆分、角色/场景、分镜和图片到视频参考链路，但它仍是工作流骨架，不是完整短剧生产线。

尚缺：

- 角色一致性与场景资产版本。
- 镜头批量生成、失败恢复和成本汇总。
- 配音、音效、字幕、时间轴和 FFmpeg 合成。
- 完整成片预览、版本、下载和发布。
- 管理端短剧模型、价格、并发和任务运营。

这些能力应继续复用 Xinyue 的项目、文件、生成、审核和计费，不复制 VOZEB 的账号、支付或后台。

8. 运营与安全：公告、通知、审核、工单、告警、登录、审计和健康。

## 10. API 页面冲突

`ApiLandingPage.vue` 当前展示以下接口：

- `/v1/chat/completions`
- `/v1/responses`
- `/v1/messages`
- `/v1beta/models/...:generateContent`

当前 NestJS 没有提供这些面向外部开发者的统一网关控制器，也没有对应的站点 API Key、开发者限流、外部用量账单和协议兼容层。因此该页面目前属于误导性界面。

已确定的低风险方向是把 `/api` 变为后台配置的第三方 API 入口；如果以后决定建设 Xinyue 自有公共 API，应作为独立项目补齐 API Key、鉴权、协议、限流、配额、账单、审计和文档，不能只保留当前静态页面。
